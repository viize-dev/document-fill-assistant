## 1. สถานะปัจจุบัน

- `lib/sources.js` ทำ Gmail + Drive ผ่าน `chrome.identity.getAuthToken` (scope `gmail.readonly`, `drive.readonly`) แต่ยังเป็นโค้ดที่ **ไม่เคยรันกับ Google จริง** (ไม่มี client_id)
- ผูกกับ Google อย่างเดียว, ไม่มีหน้าจัดการบัญชี, ไม่มี disconnect, ไม่มี pagination, ไม่ตรวจขนาด/ชนิดไฟล์, ไม่จำว่าไฟล์ไหนทำแล้ว
- `getAuthToken` ใช้ได้เฉพาะ Chrome ที่ผู้ใช้ sign in โปรไฟล์ Google ไว้ (Edge/Brave/โปรไฟล์ไม่ sign in ใช้ไม่ได้)

## 2. หลักการออกแบบ

1. **Source adapter** รูปแบบเดียวกับ provider AI: เพิ่มแหล่งใหม่ = เพิ่มไฟล์ ไม่แก้ side panel
2. **อ่านอย่างเดียว ขอ scope น้อยที่สุด** ไม่มี scope ส่งเมล/ลบ/แก้ไข
3. **token อยู่ในเครื่องผู้ใช้เท่านั้น** ไม่ส่งไป backend ใดๆ (PDF ไปเฉพาะผู้ให้บริการ AI ที่ผู้ใช้เลือก หรือไม่ไปไหนเลยในโหมดในเครื่อง)
4. ไฟล์จากเมลคือ **ข้อมูลไม่น่าเชื่อถือ**: ตรวจ magic bytes `%PDF`, จำกัดขนาด, แสดงชื่อ/ผู้ส่งด้วย `textContent` เท่านั้น (ทำอยู่แล้ว), ไม่เปิดลิงก์ในเมล
5. ต้องใช้งานได้แม้ไม่ได้เชื่อมบัญชี: อัปโหลดไฟล์ / โฟลเดอร์ในเครื่องคงอยู่เสมอ

## 3. แหล่งไฟล์ที่รองรับ (ลำดับความสำคัญ)

| แหล่ง | วิธี | auth | หมายเหตุ |
|---|---|---|---|
| อัปโหลด/ลากวาง | มีแล้ว | - | |
| **Google Drive** | Drive API (list/download) | `drive.readonly` | ⚠ restricted scope; Picker + `drive.file` ใช้ใน MV3 ไม่ได้ (ดูการตัดสินใจด้านบน) |
| **Gmail** | Gmail API (list/get attachment) | `gmail.readonly` | ⚠ เป็น restricted scope: ขึ้นเตือน "unverified app" จนกว่าจะผ่านการตรวจสอบแอป และอาจต้องมีการประเมินความปลอดภัยโดยหน่วยตรวจของ Google (มีค่าใช้จ่าย/ทำซ้ำรายปี) ต้องตรวจว่ากรณี "ประมวลผลในเครื่อง แต่ส่ง PDF ให้ AI ของผู้ใช้เอง" ถูกนับอย่างไร |
| **Microsoft 365 / Outlook / OneDrive** | Microsoft Graph | `Mail.Read`, `Files.Read` (delegated), OAuth code + PKCE | ผู้ใช้ยินยอมเองได้ในส่วนใหญ่ แต่ ⚠ บางองค์กรปิดและต้องให้ผู้ดูแล tenant อนุมัติ; ควรทำ publisher verification |
| **โฟลเดอร์ในเครื่อง** | File System Access API (`showDirectoryPicker`) | ไม่ต้อง login | ใช้กับโฟลเดอร์ที่โปรแกรมสแกนเนอร์/ระบบอื่นวางไฟล์ไว้ ไม่ติดเรื่องการตรวจแอป |
| Dropbox / Box | API ของแต่ละเจ้า | OAuth PKCE | ทำเมื่อมีลูกค้าขอจริง |
| IMAP (เมลองค์กรทั่วไป) | **ทำจาก extension ตรงๆ ไม่ได้** (เบราว์เซอร์ไม่มี TCP) | - | ต้องมี backend คอยดึง = ต้องเก็บรหัส/token เมลของผู้ใช้ไว้ฝั่งเรา ไม่แนะนำ ทางเลือก: ให้ผู้ใช้ forward เข้า Gmail/Outlook หรือบันทึกลงโฟลเดอร์ |

ทางเลือกลดภาระการตรวจของ Gmail: ตั้งกฎให้เมลที่มี PDF ถูกบันทึกลง Drive อัตโนมัติ (Apps Script / Power Automate) แล้วดึงผ่าน Drive Picker (`drive.file`) แทน — ใช้ได้เมื่อหน่วยงานยอมตั้งกฎ (ใน MV3 ยังต้องใช้ `drive.readonly` อยู่ดี จึงไม่ช่วยเรื่อง restricted scope)

**ต้องถามลูกค้าก่อนเลือกว่าเริ่มที่ใด:** หน่วยงานใช้เมลระบบไหน (Google Workspace / Microsoft 365 / เมลรัฐ / อื่นๆ) และ PDF ส่วนใหญ่เข้ามาทางไหน (เมล / สแกนลงโฟลเดอร์ / ไดรฟ์)

## 4. สถาปัตยกรรม

```
lib/sources/
  index.js        registry: SOURCES = { upload, folder, google-drive, gmail, ms-mail, ms-drive }
                  แต่ละแหล่ง: { id, label, kind: 'upload'|'folder'|'oauth', provider?, ... }
  auth/
    google.js     getToken(interactive), revoke()      (chrome.identity.getAuthToken; สำรอง launchWebAuthFlow)
    microsoft.js  login(), getToken(), revoke()        (launchWebAuthFlow + PKCE, เก็บ refresh token)
    store.js      อ่าน/เขียน token + บัญชีที่เชื่อมใน chrome.storage.local, ล้างตอน disconnect
  gmail.js  drive.js  msmail.js  onedrive.js  folder.js
  guard.js        ตรวจก่อนส่งต่อ: ขนาด ≤ 20 MB, magic bytes, นามสกุล/ชนิด, จำนวนต่อครั้ง
  history.js      จำ id ที่ประมวลผลแล้ว (ไม่เก็บเนื้อหา) เพื่อขึ้นป้าย "ทำแล้ว"
```

อินเทอร์เฟซของแต่ละแหล่ง:

```js
{
  status(): Promise<{connected, account?}>,
  connect(): Promise<void>,        // ต้องมาจากการคลิกของผู้ใช้
  disconnect(): Promise<void>,     // ลบ token + เรียก revoke
  list({ query, filters, cursor }): Promise<{ items: Item[], nextCursor? }>,
  download(item): Promise<Blob>,
}
// Item = { id, source, name, meta, size?, date? }  -> ไหลต่อเข้า setFile() เดิม ไม่ต้องแก้ pipeline
```

รายละเอียดสำคัญ:
- **Google**: ใช้ `getAuthToken` เป็นหลัก (refresh เงียบให้) เพิ่มทางสำรอง `launchWebAuthFlow` สำหรับเบราว์เซอร์ที่ไม่รองรับ (ได้ token อายุสั้น ~1 ชม. ต้องขออนุญาตใหม่เมื่อหมด)
- **Microsoft**: ลงทะเบียนแอปแบบ SPA/public client, redirect `https://<extension-id>.chromiumapp.org/` (extension id ต้องคงที่: กำหนด `key` ใน manifest), authorization code + PKCE, เก็บ refresh token ใน `chrome.storage.local`
- **MV3**: service worker ถูกปิดได้ทุกเมื่อ จึงห้ามเก็บสถานะ login ไว้ในตัวแปร ให้อ่านจาก storage ทุกครั้ง
- **Gmail**: ค้นหาด้วย query ของ Gmail (`has:attachment filename:pdf newer_than:30d`), แบ่งหน้าด้วย `pageToken`, ดึงรายการแบบ batch/ขนานแทนยิงทีละฉบับ (ตอนนี้ยิงต่อเนื่องทีละฉบับ ช้าและเปลือง quota), ไฟล์แนบอยู่ซ้อนใน multipart ต้อง walk หลายชั้น (ทำแล้ว) และกรณี Drive link ในเนื้อเมลเป็นขอบเขตเฟสหลัง
- **Drive**: ใช้ Picker แทนการ list ทั้งไดรฟ์ ถ้ายังต้องการ list ต้องใช้ `drive.readonly` (restricted) จึงเลี่ยง; ไฟล์ Google Docs ต้อง export เป็น PDF (`files/{id}/export`) ส่วนไฟล์ PDF ใช้ `alt=media`
- **Folder**: เก็บ `FileSystemDirectoryHandle` ใน IndexedDB (เก็บ handle ได้ ต้องขอสิทธิ์ใหม่เมื่อเปิดครั้งถัดไป), แสดง PDF เรียงตามวันที่แก้ล่าสุด

## 6. ความปลอดภัยและความเป็นส่วนตัว

- scope อ่านอย่างเดียวเท่านั้น และขอเมื่อผู้ใช้กดเชื่อมต่อ ไม่ขอล่วงหน้า
- token อยู่ใน `chrome.storage.local` ของ extension (ไม่เข้ารหัสเพิ่มได้ เพราะ extension ไม่มีที่เก็บ secret) จึงต้อง: ไม่ log, ล้างเมื่อ disconnect, ไม่ส่งออกนอก origin ของผู้ให้บริการนั้น
- ไม่มี backend คั่น: ไม่มีเซิร์ฟเวอร์ของเราเห็นเมลผู้ใช้
- เนื้อหาเมลที่แสดง (ผู้ส่ง/หัวเรื่อง/ชื่อไฟล์) เป็นข้อมูลที่ผู้โจมตีกำหนดได้ → `textContent` เท่านั้น และห้ามนำไปเป็นคำสั่งให้ AI (prompt ของเรารับเฉพาะตัว PDF; ข้อความใน PDF ก็ถือเป็นข้อมูล ไม่ใช่คำสั่ง — ควรเพิ่มประโยคนี้ใน `buildPrompt`)
- ต้องมี **นโยบายความเป็นส่วนตัว** สาธารณะ ระบุว่าอ่านอะไร ไปที่ไหน (ถ้าใช้โหมด AI ไฟล์ถูกส่งไปค่ายที่ผู้ใช้เลือก) — จำเป็นทั้งสำหรับการตรวจแอปของ Google/Microsoft และ Chrome Web Store
- ⚠ นโยบายข้อมูลของ Google (Limited Use) จำกัดการส่งข้อมูลจาก Gmail ให้บุคคลที่สาม ต้องอ่านว่าการส่ง PDF ให้ AI ของผู้ใช้เองเข้าข่ายอนุญาตหรือไม่ และต้องเปิดเผยในหน้า consent

## 7. ใครเป็นเจ้าของ OAuth app (ตัดสินใจก่อนเริ่ม)

| แบบ | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. เราเป็นเจ้าของแอปเดียว ขายให้ทุกลูกค้า** | ลูกค้าติดตั้งแล้วใช้เลย | ต้องผ่านการตรวจแอป Google/Microsoft เอง (เวลา+ค่าใช้จ่าย), ความรับผิดชอบเรื่องข้อมูลอยู่ที่เรา |
| **B. ลูกค้าแต่ละหน่วยงานสร้าง OAuth client ของตัวเอง** (Google Workspace ตั้งเป็น Internal / Entra app ใน tenant ตัวเอง) | ไม่ต้องผ่านการตรวจสาธารณะ ข้อมูลอยู่ใต้การควบคุมของหน่วยงาน | ต้องมีขั้นตอนติดตั้ง/เอกสารต่อลูกค้า ใส่ client_id ได้ในตั้งค่า (ต้องเปลี่ยนจาก manifest `oauth2` ซึ่งตายตัว เป็น `launchWebAuthFlow` ที่รับ client_id จากตั้งค่า) |
| **C. ช่วงทดลอง: โหมด Testing ของ Google** | เริ่มได้ทันที จำกัด ~100 ผู้ใช้ทดสอบที่ต้องเพิ่มรายชื่อเอง | ⚠ token ของแอป Testing อายุสั้น (ราว 7 วัน) ใช้จริงจังไม่ได้ |

คำแนะนำ: เฟสแรกใช้ C เพื่อพิสูจน์ flow, ขายจริงเริ่มด้วย **B** สำหรับลูกค้าหน่วยงานรัฐ (ควบคุมข้อมูลเองได้ ซึ่งตรงกับความละเอียดอ่อนของเอกสารราชการ) แล้วค่อยทำ A เมื่อมีลูกค้ารายย่อยจำนวนมาก

## 8. แผนเป็นเฟส

**เฟส 0 — ตัดสินใจ (1–2 วัน)**
- ถามลูกค้าเรื่องระบบเมล/แหล่งไฟล์, เลือกแบบเจ้าของ app (ข้อ 7), ยืนยันนโยบาย ⚠ ของ Google/Microsoft
- ผลลัพธ์: รายการแหล่งที่จะทำเฟสแรก

**เฟส 1 — โครงสร้างและความแข็งแรง (2–3 วัน)** ✅ เสร็จแล้ว ไม่ต้องมีบัญชีจริง ทดสอบด้วย mock ได้ (หน้า "บัญชีที่เชื่อมต่อ" ทำเป็นสถานะ+ปุ่มยกเลิกในแต่ละแท็บแทนหน้าตั้งค่าแยก; ยังไม่ได้ตรึง extension id ใน manifest ให้ทำพร้อมเฟส 2 เมื่อสร้าง OAuth client)
- แยก `lib/sources.js` เป็น adapter ตามข้อ 4, `guard.js`, `history.js`, ตรึง `key`/extension id ใน manifest
- pagination, ตัวกรอง, ข้อความผิดพลาดภาษาไทย, หน้า "บัญชีที่เชื่อมต่อ" + disconnect
- เพิ่มแหล่ง **โฟลเดอร์ในเครื่อง** (ไม่ต้อง login)
- เสร็จเมื่อ: unit test ผ่านด้วย `fetch` จำลอง (หน้าแรก/หน้าถัดไป/401/403/429/ไฟล์ใหญ่/ไม่ใช่ PDF), side panel ทดสอบในเบราว์เซอร์ด้วย adapter จำลอง

**เฟส 2 — Google จริง (3–4 วัน)**
- สร้างโปรเจกต์ Google Cloud + OAuth client (โหมด Testing) ใส่ `oauth2.client_id`, scope `gmail.readonly` + `drive.readonly` และ **เริ่มเตรียมเอกสารยื่นตรวจแอป** (โดเมน, นโยบายความเป็นส่วนตัว, วิดีโอสาธิต)
- ทดสอบกับบัญชีจริง: เมลหลายไฟล์แนบ, multipart ซ้อน, ไฟล์ใหญ่, token หมดอายุ, ผู้ใช้กดปฏิเสธ, ไม่ได้ sign in Chrome (ใช้ทางสำรอง)
- เสร็จเมื่อ: ผู้ใช้ทดสอบ 2–3 คนดึง PDF จาก Gmail และ Drive แล้วกรอกฟอร์มสำเร็จ

**เฟส 3 — Microsoft (3–4 วัน)**
- ลงทะเบียนแอปใน Entra, `launchWebAuthFlow` + PKCE + refresh, Outlook (Graph `me/messages` + attachments), OneDrive
- ทดสอบทั้งบัญชีส่วนตัวและ tenant องค์กรที่ปิด user consent (ต้องแสดงข้อความให้ขอ admin)

**เฟส 4 — พร้อมขาย (เวลาขึ้นกับการตรวจแอป)**
- นโยบายความเป็นส่วนตัว + หน้าอธิบายสิทธิ์, ส่งตรวจแอป Google (ถ้าเลือกแบบ A หรือใช้ Gmail สาธารณะ) / publisher verification ของ Microsoft, ส่ง Chrome Web Store
- ถ้าเลือกแบบ B: เขียนคู่มือให้ผู้ดูแลหน่วยงานสร้าง client_id และช่องใส่ใน "ตั้งค่า" (เก็บต่อ profile/องค์กร)

**เฟส 5 — ส่วนเสริม (เมื่อมีคนขอ)**
- เลือกหลายไฟล์ + คิว, ตั้งตัวกรองประจำหน่วยงาน (ผู้ส่ง/label/โฟลเดอร์), ดึงลิงก์ Drive ในเนื้อเมล, Dropbox/Box

## 9. การทดสอบ

- unit: adapter ทุกตัวด้วย `fetch` จำลอง (รูปแบบเดียวกับ test ของ provider AI), `guard`, `history`
- เชิงบูรณาการ: บัญชีทดสอบจริงของแต่ละผู้ให้บริการ (เฟส 2–3) บันทึกผลลง README ว่าทดสอบอะไรแล้ว/ยังไม่ได้ทดสอบ
- ห้ามใช้เมลจริงของลูกค้าในการทดสอบ ใช้บัญชีทดสอบและ PDF ตัวอย่างใน `samples/`

## 10. ความเสี่ยง

| ความเสี่ยง | ผล | ทางลด |
|---|---|---|
| Gmail restricted scope ใช้เวลา/เงินในการตรวจ | ขายเป็นสาธารณะช้า | แบบ B, ทางเลือกบันทึกลง Drive, เริ่มที่ Drive Picker |
| Tenant องค์กรปิด user consent | ผู้ใช้เชื่อมไม่ได้ | ข้อความอธิบาย + คู่มือให้ admin อนุมัติ |
| ผู้ใช้ไม่ได้ sign in Chrome / ใช้ Edge | `getAuthToken` ใช้ไม่ได้ | ทางสำรอง `launchWebAuthFlow` |
| token ในเครื่องถูกขโมย (มัลแวร์/เครื่องร่วม) | อ่านเมลได้ | scope อ่านอย่างเดียว, ปุ่ม disconnect/revoke, เตือนเรื่องเครื่องสาธารณะ |
| เมลมี PDF อันตราย/ข้อความหลอก AI | ข้อมูลผิด | guard ไฟล์, pdf.js ปิด eval (ทำแล้ว), ผู้ใช้ตรวจก่อนกรอก (ทำแล้ว), prompt ระบุว่าข้อความในไฟล์เป็นข้อมูล |
| โควตา API / rate limit | โหลดรายการช้าหรือล้มเหลว | โหลดเป็นหน้า, backoff เมื่อ 429 |

## 11. สิ่งที่ต้องให้ผู้ใช้ตัดสินใจ

1. ลูกค้ากลุ่มแรกใช้เมล/ไดรฟ์ระบบไหน และ PDF เข้ามาทางไหนเป็นหลัก
2. เจ้าของ OAuth app: A / B / C (ข้อ 7)
3. ยอมรับการเลี่ยง Gmail สาธารณะในรุ่นแรก (ใช้ Drive Picker + โฟลเดอร์ + ตั้งกฎบันทึกเมลลง Drive) เพื่อเลี่ยงการตรวจแอปหรือไม่

## สิ่งที่ถูกตัดออกจาก manifest ในรุ่นอัปโหลดอย่างเดียว

`oauth2` (client id + scope) และ host ของ Gmail / Google APIs / Microsoft Graph ถูกย้ายไปเก็บที่ `docs/manifest-sources-permissions.json` กลับมาทำให้ใส่คืนใน `manifest.json` แล้วเปิดสวิตช์ใน `lib/sources/config.js`
