## 0. ทิศทางที่ตกลง (จากหัวหน้าทีม)

1. **รุ่นแรกมีแค่ "อัปโหลดเอกสาร"** ยังไม่ทำ Gmail / Drive / Outlook / OneDrive / โฟลเดอร์ ทั้งหมด **พักไว้** (ดู `PLAN-sources.md`)
2. **หน้าตั้งค่า API key ไม่ให้ผู้ใช้เห็น** ย้ายไปหลังบ้าน ให้ **admin คนเดียว** เข้าไปตั้งค่า ผู้ใช้แค่ login แล้วใช้งาน
3. **ทำสรุปเอกสาร** แล้วนำไปกรอกในใบปะหน้า

## 3. ส่วน B: หลังบ้านให้ admin ตั้งค่า API key

### B.1 เป้าหมายและหลักการ

- ผู้ใช้ทั่วไป **ไม่เห็นและไม่ต้องรู้จัก API key**: เปิด extension → login บัญชีองค์กร → ใช้งาน
- **admin คนเดียว** เป็นผู้เดียวที่ตั้งค่า key / โมเดล / โควต้า / สิทธิ์เข้าใช้ได้
- key **เก็บเข้ารหัสฝั่งเซิร์ฟเวอร์ ไม่ส่งกลับมาแสดงอีก** (เขียนอย่างเดียว เห็นแค่ 4 ตัวท้าย)
- ย้ายการสร้าง prompt มาฝั่งเซิร์ฟเวอร์ (ปิดช่องที่ผู้ใช้ส่ง prompt อะไรก็ได้ ตามที่ README ของ backend ระบุเป็นข้อจำกัด)
- ไม่เก็บเนื้อหาเอกสาร เก็บเฉพาะ metadata การใช้งาน

### B.2 สถาปัตยกรรม

```
Extension (ผู้ใช้)                    Backend (ต่อองค์กร)                     ค่าย AI
 login OIDC ──────────────────────▶  /auth/oidc → session token
 ส่ง PDF + profile/doc type ───────▶  /v1/extract : สร้าง prompt ฝั่ง server
                                       ดึง key (ถอดรหัส) ──────────────────▶  Claude / OpenAI / Gemini
 รับ fields + summary ◀────────────   ตรวจโควต้า, บันทึก usage (ไม่เก็บไฟล์)

Admin (เบราว์เซอร์)
 เข้า https://<backend>/admin ──────▶  Admin console (หน้าเว็บเล็กๆ ที่ backend ให้บริการเอง)
```

**โมเดลการติดตั้ง: 1 องค์กร = 1 backend (single-tenant)** ตามที่ backend ทำไว้แล้ว แต่ละลูกค้า deploy เอง (Docker อยู่แล้ว) ข้อมูลเอกสารราชการไม่ผ่านเซิร์ฟเวอร์ของเรา

### B.3 สิ่งที่ admin ตั้งค่าได้ (ย้ายจากไฟล์ → ฐานข้อมูล แก้ผ่านหน้าเว็บ)

| หมวด | ตั้งอะไรได้ |
|---|---|
| ผู้ให้บริการ AI และ key | เลือกค่าย (Claude / OpenAI / Gemini), ใส่ key, **ปุ่มทดสอบ key** (เรียก list models), หมุน/ลบ key, ดูแค่ 4 ตัวท้ายและวันที่ตั้ง |
| โมเดล | เลือกโมเดลที่เปิดให้ผู้ใช้, โมเดลเริ่มต้น (รายการโหลดจากค่ายจริง เพราะ ID เปลี่ยนบ่อย) |
| สิทธิ์เข้าใช้ | โดเมน/อีเมลที่อนุญาต, รายการผู้ใช้ที่เคยเข้า, ระงับผู้ใช้ |
| โควต้า | ต่อผู้ใช้/เดือน, ต่อนาที, ขนาดไฟล์สูงสุด |
| ฟีเจอร์ | เปิด/ปิดสรุปเอกสาร, อนุญาตโหมดในเครื่องหรือไม่ |
| รายงาน | การใช้งานต่อผู้ใช้/เดือน, ประมาณค่าใช้จ่ายจาก token (ไม่ใช่ใบแจ้งหนี้) |
| Audit log | ใครเปลี่ยนอะไรเมื่อไร (ไม่มีค่าความลับ) |

ค่าที่ต้องมีก่อนเริ่มระบบ (ตั้งผ่าน env/ไฟล์ ไม่ใช่หน้าเว็บ): พอร์ต, ที่เก็บฐานข้อมูล, `JWT_SECRET`, **`MASTER_KEY`** (กุญแจเข้ารหัส key ของค่าย AI เก็บแยกจากฐานข้อมูล), ข้อมูล OIDC, อีเมล admin

### B.4 "admin คนเดียว" ออกแบบอย่างไร

- มี **admin หนึ่งบัญชี** กำหนดตอนติดตั้ง (`ADMIN_EMAIL`) บัญชีอื่นแม้จะอยู่ในโดเมนก็เข้าหน้า admin ไม่ได้ (ต่างจากตอนนี้ที่ `adminEmails` เป็นรายการ)
- login หน้า admin ผ่าน OIDC ของค่ายเดียวกับผู้ใช้ แต่ใช้ **authorization code + PKCE ฝั่งเซิร์ฟเวอร์** (ต้องลงทะเบียน redirect URI เพิ่ม `https://<backend>/admin/callback`) เพราะหน้าเว็บไม่มี `chromiumapp.org` ให้ใช้
- กรณี admin เข้าไม่ได้ (ลาออก/ลืม/IdP ล่ม): **คำสั่งกู้คืนทาง CLI** บนเซิร์ฟเวอร์ (`npm run admin:set -- <email>`) ต้องมีสิทธิ์เข้าเครื่องเซิร์ฟเวอร์ถึงจะทำได้ ไม่มีช่องทางผ่านเว็บ
- ⚠ ข้อเสียที่ควรบอกลูกค้า: คนเดียวเป็นจุดเสี่ยง (single point) ควรมีขั้นตอนส่งต่อ admin ที่เขียนไว้ใน README

### B.5 ความปลอดภัย (ข้อบังคับของส่วนนี้)

- เข้ารหัส key ด้วย AES-256-GCM, `MASTER_KEY` อยู่ใน env/secret manager ไม่อยู่ในฐานข้อมูลหรือ repo, ไม่ส่ง key กลับไปที่หน้าเว็บทุกกรณี
- ไม่ log ค่า key, ข้อความผิดพลาดจากค่าย AI ต้องกรองไม่ให้มี key หลุด
- คุกกี้ admin: `HttpOnly; Secure; SameSite=Strict`, หมดอายุเมื่อไม่ใช้งานราว 30 นาที, header กัน CSRF, CSP เข้ม, จำกัดจำนวนครั้ง login
- เส้นทาง `/admin/*` ตรวจสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ทุกครั้ง ผู้ใช้ทั่วไปได้ 403
- Audit log ทุกการเปลี่ยนค่า (เก็บใคร/อะไร/เมื่อไร ไม่เก็บค่า)
- ต้องเป็น HTTPS เท่านั้น (ถ้าไม่ใช่ server ไม่ยอมเริ่ม ทำอยู่แล้วบางส่วน)
- เพิกถอน session ก่อนหมดอายุได้ (ตอนนี้ยังทำไม่ได้)
- ⚠ PDPA: PDF ผ่านเซิร์ฟเวอร์ของลูกค้าไปค่าย AI ภายนอก ต้องมีข้อความแจ้งผู้ใช้และข้อตกลงกับค่าย AI เรื่องการไม่นำข้อมูลไปเทรน (ตรวจเงื่อนไขของแต่ละค่ายปัจจุบันก่อนขาย)

### B.6 ฝั่ง Extension

| ตอนนี้ | หลังทำ |
|---|---|
| หน้าตั้งค่ามีเลือกค่าย + ช่อง API key + ทดสอบ key | **โหมดองค์กร:** ซ่อนทั้งหมด เหลือ "บัญชี: x@org (ออกจากระบบ)" และการใช้งานเดือนนี้ |
| ผู้ใช้ใส่ URL backend เอง | URL มาจาก **นโยบายองค์กร** (`chrome.storage.managed`, ผู้ดูแล IT ตั้งผ่าน Chrome policy) หรือค่าเริ่มต้นตอน build ต่อลูกค้า หรือกรอกครั้งเดียวตอนเปิดใช้ครั้งแรก |
| ส่ง prompt ไปที่ backend | ส่ง `profile id + ชนิดเอกสาร` ให้ server สร้าง prompt |
| โหมด API key ส่วนตัว | เก็บไว้เป็น **build แยก** (ซ่อนในรุ่นลูกค้าองค์กร) ถ้ายังต้องขายแบบไม่มี backend — ⚠ ต้องตัดสินใจ (ข้อ 6) |

⚠ ข้อควรระวัง: การย้าย prompt ไป server หมายถึง server ต้องมีนิยามฟิลด์/ชนิดเอกสารของแต่ละ profile ด้วย ต้องแยก `profiles/*.js` เป็นแพ็กเกจ JSON ที่ใช้ร่วมกัน (ไม่ให้สองฝั่งไม่ตรงกัน)

## 4. ส่วน C: สรุปเอกสารลงใบปะหน้า

### C.1 ผลลัพธ์ที่ต้องการ

- ได้ **"สรุปเรื่อง" ภาษาไทยสั้นๆ 2–3 ประโยค** (กรอบจำนวนตัวอักษรตั้งใน profile เช่น `cover.summaryMax`, ค่าตั้งต้น ~200 ตัวอักษร) บอกว่า: ใครขออะไร / เหตุผลสำคัญ / ให้ทำอะไร ภายในเมื่อไร
- แสดงในหน้าตรวจข้อมูลเป็นช่อง **แก้ไขได้** พร้อมตัวนับตัวอักษร และไปปรากฏในใบปะหน้า
- วันที่กำหนดและประโยคปิดท้ายที่ดึงได้อยู่แล้ว ใช้ร่วมกัน (ติ๊กตัวเลือก "เพื่อโปรดพิจารณา/ดำเนินการ")

### C.2 การทำงาน

| โหมด | วิธี | หมายเหตุ |
|---|---|---|
| AI | ปรับ prompt ให้ได้ `summary` (≤ ความยาวที่กำหนด) กับ `requested_action` แยกกัน ขอเป็น JSON เดียวกับการดึงฟิลด์ (ไม่เพิ่มการเรียก AI) | กติกา: เฉพาะข้อเท็จจริงในเอกสาร ตัวเลข/วันที่/ชื่อคัดลอกตรง ห้ามเดา ข้อความในเอกสารเป็น "ข้อมูล" ไม่ใช่คำสั่ง |
| ในเครื่อง (ไม่ใช้ AI) | **สรุปจริงไม่ได้** ทำร่างแบบตัดประโยคสำคัญ (ประโยคที่มี "ขอ/เพื่อ/ภายใน/จึง" ต่อจากส่วนหัว) ติดป้าย "ร่าง ไม่ได้สรุปด้วย AI กรุณาตรวจ" ความมั่นใจต่ำ | บอกลูกค้าตรงๆ ว่าคุณภาพต่างจากโหมด AI |
| หลังบ้าน | เปิด/ปิดฟีเจอร์ได้, สรุปด้วยโมเดลที่ admin เลือก | |

### C.3 ใบปะหน้า: วางสรุปตรงไหน (ต้องตัดสินใจ)

ใบปะหน้าปัจจุบันมีแถวว่าง 2 แถวในกรอบ ใต้ตัวเลือก "เพื่อโปรด..." และเส้นเขียนความเห็นด้านล่าง

| ตัวเลือก | ข้อดี/ข้อเสีย |
|---|---|
| **ก. แถวว่าง 2 แถวในกรอบ (แนะนำ)** | อยู่ใกล้ตัวเลือกที่ติ๊ก อ่านต่อเนื่อง ไม่เปลี่ยนรูปแบบกลาง; จำกัดราว 2 บรรทัด |
| ข. ช่อง "หมายเหตุ" | พื้นที่เท่ากัน แต่ผู้ใช้มักเขียนหมายเหตุเอง จึงชนกัน |
| ค. เพิ่มกรอบ "สรุปเรื่อง" ใต้เรื่อง | พื้นที่มาก แต่เปลี่ยนรูปแบบแบบฟอร์มกลางที่ลูกค้าให้มา |

ผมแนะนำ **ก.** และถ้าสรุปยาวเกิน ให้ตัดตอนพิมพ์พร้อมเตือน ไม่ล้นหน้า (ตอนนี้ใบปะหน้าพิมพ์ 1 หน้า A4 พอดี ต้องรักษาไว้)

### C.4 การวัดคุณภาพ

สรุปให้ตัดสินด้วยตัวเลขตรงๆ ไม่ได้ จึงวัดหลายชั้น:
1. **อัตโนมัติ:** ความยาวไม่เกินกรอบ, เป็นภาษาไทย, **ตัวเลข/วันที่/เลขที่ในสรุปต้องมีอยู่ในข้อความต้นฉบับ** (กันแต่งเอง), ไม่มีคำสั่งหลุดมาจากเอกสาร
2. **ครอบคลุมใจความ:** เพิ่ม `key_points` ในชุดตัวอย่าง (`samples/expected.json`) ว่าต้องมีอะไรอย่างน้อย (ผู้ขอ/เรื่อง/กำหนดเวลา) แล้วนับว่าครบเท่าไร
3. **คนตรวจ:** เอกสารจริง 10 ฉบับ ให้เจ้าหน้าที่ให้คะแนน 1–5 ว่า "ใช้ได้โดยไม่ต้องแก้" กี่ฉบับ
- ⚠ ตัวอย่างในโปรเจกต์ตอนนี้เป็นเอกสารสมมติ ผลวัดจากเอกสารจริงอาจต่างมาก

### C.5 เฟสย่อยของส่วน C

| เฟส | งาน | ผลลัพธ์ |
|---|---|---|
| C-1 (1–2 วัน) | ปรับ prompt (`summary` + `requested_action`), เพิ่มฟิลด์ "สรุปเรื่อง" ใน profile + แถวแก้ไขได้พร้อมตัวนับ | ทดสอบ unit ของ prompt/แถว |
| C-2 (1 วัน) | ใบปะหน้า: ใส่สรุปในตำแหน่งที่เลือก, ตัดเมื่อเกิน, พิมพ์ 1 หน้า | ตรวจภาพ + พิมพ์ทดสอบ |
| C-3 (1–2 วัน) | โหมดในเครื่อง: ร่างสรุปแบบตัดประโยค + ป้ายเตือน | ทดสอบกับตัวอย่าง |
| C-4 (2 วัน) | เพิ่มการวัดคุณภาพ (ข้อ C.4) และรันกับค่ายจริงด้วย key ทดสอบ | รายงานผล |

## 5. ลำดับงานที่แนะนำ

1. **A** (ทันที) → รุ่นอัปโหลดอย่างเดียวพร้อมใช้
2. **C-1, C-2** (สรุปลงใบปะหน้า) ไม่ต้องรอหลังบ้านและเห็นผลกับผู้ใช้เร็วที่สุด
3. **B-1 → B-3** (admin ตั้งค่า key + extension โหมดองค์กร)
4. **C-3, C-4** และ **B-4, B-5**

ลำดับ 2 และ 3 ทำคู่ขนานได้ (ไฟล์ที่แก้ไม่ซ้อนกัน)

รวมคร่าวๆ: A ≈ 0.5 วัน, C ≈ 5–7 วัน, B ≈ 12–16 วัน (ประมาณการ ยังไม่รวมการรอข้อมูลจากลูกค้า/IdP จริง)

## 6. การตัดสินใจ (ข้อ 1, 2, 4, 7 ยืนยันตามที่แนะนำแล้ว; ข้อ 3, 5, 6 ยังรอข้อมูลจากลูกค้า)

1. **ที่วางสรุปในใบปะหน้า:** ก (แถวว่างในกรอบ) / ข / ค — แนะนำ ก
2. **โมเดลการติดตั้งหลังบ้าน:** ลูกค้า deploy เอง 1 องค์กร = 1 เซิร์ฟเวอร์ (แนะนำ) หรือเราโฮสต์ให้ทุกราย (ต้องรองรับหลายองค์กรใน instance เดียว งานเพิ่มมาก และเราต้องรับผิดชอบข้อมูล)
3. **ยังขายแบบไม่มีหลังบ้านไหม** (ผู้ใช้ใส่ key เอง): ถ้าไม่ขาย ตัดโหมด key ส่วนตัวออกจากรุ่นลูกค้าได้ ถ้าขาย ต้องแยก build
4. **วิธี login admin:** OIDC ผ่านค่ายเดียวกับผู้ใช้ (แนะนำ) หรือรหัสผ่าน+TOTP ของระบบเอง
5. **ผู้ติดตั้งหลังบ้านคือใคร:** ทีมเรา หรือ IT ของลูกค้า (มีผลต่อเอกสารและความง่ายของขั้นตอนติดตั้ง)
6. **ใครเป็น admin ของลูกค้าแต่ละราย** และมีผู้สำรองหรือไม่ (ดู B.4)
7. **ความยาวสรุปสูงสุดในใบปะหน้า** ตามแบบฟอร์มจริงของลูกค้า
