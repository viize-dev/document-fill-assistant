# แผนงาน: ตรวจจับช่อง input ของหน้าจออัตโนมัติ (Field Discovery)

สถานะ (2026-10-21): **F1, F2 และส่วนหลักของ F3 ทำแล้ว** (สแกน, จับคู่ด้วยกฎ+พจนานุกรม, ความจำ, โหมดชี้ช่อง, UI ยืนยัน) ยังไม่ทำ: schema `forms[]` หลายฟอร์มใน profile เดียว, F4 (AI), F5 (แชร์ทั้งองค์กร)
ผลทดสอบเว็บจริง: ดูหัวข้อ "ผลทดสอบ" ท้ายไฟล์ ข้อตัดสินใจที่ใช้ไปก่อนรอคำตอบ: เริ่ม F1–F3 ไม่ใช้ AI, ความจำเก็บในเครื่อง, ช่องความมั่นใจกลาง/ต่ำต้องผู้ใช้ติ๊ก "ใช้" หรือกด "กรอก" เอง
ข้อจำกัดที่เปลี่ยนจากแผน: iframe ข้ามโดเมนสแกนไม่ได้ (นับและเตือน) รองรับเฉพาะ iframe โดเมนเดียวกันและ shadow DOM แบบ open

## 1. ปัญหา

ตอนนี้ extension รู้จักหน้าจอผ่าน profile (`profiles/*.js`) ที่ระบุ selector ของแต่ละช่องไว้ตายตัว ข้อจำกัด:

- ระบบสารบรรณมีหลายหน้ากรอก (ลงรับ, ลงส่ง, หนังสือเวียน, บันทึกข้อความ, แก้ไขทะเบียน ฯลฯ) ต้องเขียน profile ทีละหน้า
- ลูกค้าแต่ละหน่วยงานใช้ระบบคนละรุ่น/คนละตัว ช่องและชื่อช่องต่างกัน
- ระบบอัปเดตแล้ว selector เปลี่ยน แล้ว extension กรอกผิดช่องหรือกรอกไม่ได้เงียบๆ

เป้าหมาย: extension **สแกนหน้าปัจจุบันเอง** ได้รายการช่อง (ชื่อ, ชนิด, ตัวเลือก) แล้วจับคู่กับฟิลด์ที่อ่านจากเอกสาร ให้กรอกถูกช่อง โดยยังเป็น **กรอกอย่างเดียว ไม่กดบันทึก**

## 2. หลักการออกแบบ

1. **จับคู่เป็นชั้นๆ จากแน่นอนไปไม่แน่นอน** profile ที่เขียนไว้ → กฎ/พจนานุกรม → AI → ให้คนยืนยัน
2. **กรอกผิดแย่กว่าไม่กรอก** ช่องที่ความมั่นใจต่ำไม่กรอกเอง ต้องให้ผู้ใช้ยืนยัน
3. **สิ่งที่เรียนรู้แล้วต้องจำ** ผู้ใช้แก้การจับคู่ครั้งเดียว ครั้งต่อไปหน้าเดิมกรอกถูกเอง
4. **ไม่ส่งค่าในฟอร์มออกไปไหน** AI เห็นแค่โครงสร้าง (ป้ายชื่อ, ชนิด, ตัวเลือก) ไม่เห็นค่าที่ผู้ใช้พิมพ์ไว้

## 3. สถาปัตยกรรม

```
หน้าเว็บ ──scan──▶ Snapshot (รายการช่อง)
                      │
        ┌─────────────┼─────────────────────┐
        ▼             ▼                     ▼
  L1 Profile      L2 กฎ+พจนานุกรม       L3 AI (ถ้าเปิด)
  (selector/       (คะแนนจาก label,       (ส่งแค่ snapshot
   form signature)  name, id, ชนิด)        ที่ไม่มีค่า)
        └─────────────┼─────────────────────┘
                      ▼
             Mapping (ช่อง ↔ canonical field + ความมั่นใจ)
                      ▼
        Side panel: ตรวจ/แก้/ยืนยัน ──▶ จำเป็น learned profile
                      ▼
                  กรอกเฉพาะที่ยืนยัน (ใช้ตัวกรอกเดิมใน content.js)
```

### 3.1 Scanner (content script)

เก็บทุกช่องที่ผู้ใช้กรอกได้: `input` (text/date/number/checkbox/radio), `select`, `textarea`, `contenteditable` และ widget ที่ห่อ select (เช่น select2 ที่ระบบจริงใช้)

ข้อมูลต่อช่อง (ไม่รวมค่า):

| ข้อมูล | ที่มา |
|---|---|
| `label` | `<label for>`, ครอบด้วย `<label>`, `aria-labelledby`/`aria-label`, `placeholder`, `title`, ข้อความ th/td ซ้ายมือในตาราง, ข้อความก่อนหน้าที่ใกล้ที่สุด |
| `name`, `id`, `class` | attribute |
| `type`, `tag` | ชนิดช่อง |
| `options` | ข้อความ+ค่าของ option (select/radio group) |
| `required`, `readonly`, `disabled`, `maxlength` | attribute |
| `visible`, `rect` | ตรวจว่าเห็นจริงและตำแหน่ง (ใช้จัดลำดับ/ไฮไลต์) |
| `selector` | selector ที่เสถียรที่สุด (id > name > data-* > เส้นทาง) |
| `frame`, `shadow` | อยู่ใน iframe/shadow DOM ไหน |

ข้อกำหนด: สแกนทุก frame ที่ได้รับสิทธิ์, เจาะ open shadow DOM, ใช้ `MutationObserver` สแกนซ้ำเมื่อหน้าเปลี่ยนแบบ SPA/โหลดฟอร์มทีหลัง (debounce)

**ข้ามเสมอ:** `password`, `hidden`, `file`, `submit/button`, ช่องที่ `disabled`/มองไม่เห็น, ช่องที่ชื่อบ่งว่าเป็นรหัสผ่าน/บัตร/OTP

### 3.2 Form signature

แฮชของชุดช่องที่เสถียร (id/name + label ที่ normalize แล้ว) ใช้แยกว่า "หน้านี้คือฟอร์มไหน" แม้ URL เหมือนกัน (เช่น ระบบใช้ `index.html#` หน้าเดียวแล้วสลับเนื้อหา) และตรวจว่าหน้าเปลี่ยนจากที่เคยเรียนรู้ไว้หรือไม่

### 3.3 Profile รองรับหลายฟอร์ม

ขยายโครงสร้าง profile จาก "1 profile = 1 ฟอร์ม" เป็น "1 profile = หลายฟอร์ม (`forms[]`)" แต่ละฟอร์มมี `detect` (เงื่อนไขว่าหน้านี้คือฟอร์มนี้), `purpose` (ลงรับ/ลงส่ง/เวียน/บันทึกข้อความ), `fields` ของตัวเอง โครงเดิมต้องยังใช้ได้ (ถือเป็น `forms` ที่มี 1 รายการ)

### 3.4 Canonical fields และฟิลด์ที่ขอจาก AI

มีชุดฟิลด์กลาง (`doc_no`, `doc_date`, `from`, `to`, `subject`, `detail`, `ref`, `attachments`, `speed`, `secret`, `deadline`, ...) แต่ละฟอร์มประกาศว่าใช้ชุดไหน prompt ที่ส่ง AI/ตัวแยกกฎจึงขอเฉพาะฟิลด์ที่ฟอร์มนั้นมีช่องรองรับ (ฟอร์มลงส่งอาจมี "ถึง" แต่ไม่มี "จาก")

### 3.5 ตัวจับคู่ (Matcher)

**L1 – Profile:** ถ้า form signature ตรงกับ profile/learned profile ใช้ mapping นั้น ความมั่นใจสูง

**L2 – กฎ + พจนานุกรม:** ให้คะแนนช่อง × canonical field จาก

- ตรงกับ synonym ไทย/อังกฤษ เช่น `subject` ← "เรื่อง", "ชื่อเรื่อง", "subject"; `doc_no` ← "เลขที่หนังสือ", "เลขที่เอกสาร", "เลขที่"; `to` ← "ถึง", "เรียน", "ส่งถึง"
- ตำแหน่งชื่อ attribute (`name`/`id` เช่น `txtwsubject`) เทียบ token
- ความเข้ากันของชนิด (วันที่ ↔ ช่อง date/รูปแบบ dd/mm/yyyy, speed ↔ select ที่ option มี "ด่วน")
- ความเข้ากันของตัวเลือก: select ต้องมี option ที่แมปกับค่าที่จะกรอกได้ ไม่งั้นลดคะแนน
- ช่องกำกวม (ได้คะแนนใกล้กันหลายฟิลด์) ถือว่าไม่ชัดเจน
- แต่ละช่องได้ฟิลด์เดียว แต่ละฟิลด์ได้ช่องเดียว (assignment ที่คะแนนรวมสูงสุด)

พจนานุกรมเก็บเป็นไฟล์ข้อมูล (`lib/discovery/synonyms.js`) ขยายได้โดยไม่แก้ตรรกะ

**L3 – AI (ไม่บังคับ):** เฉพาะช่องที่ L2 ไม่ชัดเจน ส่ง snapshot ที่ตัดค่าออก + รายการ canonical field ให้โมเดลคืนคู่ mapping พร้อมเหตุผลสั้นๆ ผ่าน provider adapter เดิม (รวมโหมดหลังบ้านองค์กร) ถ้าเป็นโหมด local ไม่มี AI ก็ข้ามชั้นนี้ ผลจาก AI ถือเป็น "ข้อเสนอ" ที่ผู้ใช้ยืนยัน ไม่กรอกเองในรอบแรก

**ระดับความมั่นใจ:**

| ระดับ | ที่มา | พฤติกรรม |
|---|---|---|
| สูง | profile / learned / L2 คะแนนสูงและไม่กำกวม | กรอกได้ตามปกติ |
| กลาง | L2 คะแนนกลาง | แสดงเตือน ให้กดกรอกเอง |
| ต่ำ/AI | L3 หรือไม่ชัดเจน | ต้องผู้ใช้ยืนยันก่อน |
| ไม่รู้จัก | ไม่มีคู่ | แสดงในรายการ "ช่องที่ยังไม่ได้จับคู่" |

### 3.6 UI (side panel)

- ส่วน "หน้านี้" แสดงฟอร์มที่ตรวจพบ (ชื่อฟอร์ม/purpose, จำนวนช่อง) และปุ่ม "สแกนใหม่"
- รายการจับคู่: ฟิลด์จากเอกสาร ↔ ช่องในหน้า พร้อมป้ายความมั่นใจ ปุ่มแก้ (dropdown เลือกช่องอื่น/ไม่กรอก)
- **โหมดชี้ช่อง:** กดแล้วคลิกช่องบนหน้าเพื่อผูกกับฟิลด์ ช่องที่โฮเวอร์ถูกไฮไลต์
- คลิกชื่อช่องใน side panel แล้วไฮไลต์ช่องนั้นบนหน้า ให้ผู้ใช้ตรวจด้วยตา
- รายการ "ช่องที่ยังไม่ได้จับคู่" (ผู้ใช้ผูกกับฟิลด์ได้ หรือทิ้ง)
- ปุ่ม "บันทึกการจับคู่หน้านี้" เก็บเป็น learned profile

### 3.7 Learned profile (ความจำ)

- เก็บใน `chrome.storage.local` คีย์ด้วย origin + form signature เก็บเฉพาะ selector/label ↔ field ไม่เก็บค่าเอกสาร
- ถ้า signature เปลี่ยน (ระบบอัปเดต) ตรวจเจอแล้วเตือน "หน้านี้เปลี่ยนไป ตรวจการจับคู่ใหม่" ไม่ใช้ของเก่าแบบเงียบๆ
- โหมดองค์กร: admin ส่งออก/นำเข้า learned profile เป็น profile JSON (ใช้ `scripts/export-profiles.mjs` ที่มีอยู่) หรืออัปโหลดเข้าหลังบ้านให้ผู้ใช้ทั้งองค์กรใช้ร่วมกัน (เฟสท้าย)
- ผู้ขายยังเขียน profile มือสำหรับระบบหลักได้เหมือนเดิม learned เป็นชั้นเสริม

## 4. ความปลอดภัย / ความเป็นส่วนตัว

- สแกนเฉพาะเมื่อผู้ใช้กด (หรือเปิดใช้) และเฉพาะ origin ที่ได้รับสิทธิ์ (optional host permissions เดิม)
- Snapshot ไม่มีค่าในช่อง ตัดข้อความยาว/ข้อมูลส่วนบุคคลที่อยู่ใน option (เช่น รายชื่อบุคคล) ก่อนส่ง AI จำกัดจำนวน option ที่ส่ง
- ไม่ส่งข้อความหน้าเว็บทั้งหน้า ไม่คลิกปุ่มใดๆ (นอกจากโหมดชี้ช่องที่เป็นแค่การเลือกองค์ประกอบ) ไม่ submit
- เนื้อหาหน้าเว็บ (label/option) เป็น **ข้อมูลที่ไม่น่าเชื่อถือ** ต้องกัน prompt injection: ข้อความในหน้าห้ามถูกตีความเป็นคำสั่ง ผลลัพธ์ AI ต้อง validate เทียบรายการช่อง/ฟิลด์ที่มีจริงเท่านั้น (ห้ามคืน selector ที่ไม่มีใน snapshot)
- ช่องอ่อนไหว (password, บัตร, OTP) ไม่เข้า snapshot

## 5. แผนเป็นเฟส

### เฟส F1: Scanner + Snapshot (ฐาน)
- `lib/discovery/scan.js` (ทำงานใน content script), label resolution หลายแบบ, ข้าม frame/shadow, ตัวกรองช่องอ่อนไหว
- ส่ง snapshot ไป side panel ผ่านข้อความเดิม
- แสดงรายการช่องดิบใน side panel (ตัวเลือกนักพัฒนา)
- **ผ่านเมื่อ:** สแกนหน้าเดโมและหน้าจริงแล้วรายการช่อง/label ถูกครบทุกช่องที่เห็น (ตรวจเทียบ profile `saraban-demo`/`saraban-rid` ที่มีอยู่)

### เฟส F2: Matcher L2 (กฎ+พจนานุกรม) และ UI ยืนยัน
- `lib/discovery/match.js`, `synonyms.js`, assignment, ระดับความมั่นใจ
- UI รายการจับคู่ + แก้ไข + ไฮไลต์ + กรอกเฉพาะที่ผ่าน
- **ผ่านเมื่อ:** บนชุดทดสอบหลายฟอร์ม จับคู่ถูก ≥ 95% ของช่องที่ควรจับ และ **กรอกผิดช่อง = 0** (ช่องกำกวมต้องตกไปเป็น "ไม่แน่ใจ")

### เฟส F3: หลายฟอร์มต่อ profile + learned profile
- ขยาย schema `forms[]` (เข้ากันได้กับของเดิม) + migration ของ `saraban.js`/`saraban-rid.js`
- Form signature, ตัวเลือกฟอร์มอัตโนมัติ, learned profile (บันทึก/โหลด/ตรวจ signature เปลี่ยน), โหมดชี้ช่อง
- prompt/ตัวแยกกฎขอเฉพาะฟิลด์ที่ฟอร์มนั้นมีช่อง
- **ผ่านเมื่อ:** ผู้ใช้แก้การจับคู่หน้าที่ไม่รู้จัก 1 ครั้ง แล้วเปิดหน้าเดิมอีกครั้งกรอกถูกโดยไม่ต้องแก้

### เฟส F4: Matcher L3 (AI) สำหรับช่องที่เหลือ
- prompt สำหรับ mapping, validate ผลลัพธ์เทียบ snapshot, ใช้ได้ทั้ง API key และหลังบ้านองค์กร (เพิ่ม endpoint/prompt ฝั่ง backend, มี parity test เหมือน prompt เดิม)
- โหมด local ข้ามชั้นนี้ แสดงรายการ "ไม่รู้จัก" ให้ผู้ใช้ผูกเอง
- **ผ่านเมื่อ:** ช่องกำกวมในชุดทดสอบถูกเสนอถูก ≥ 90% และไม่มีการเสนอ selector นอก snapshot

### เฟส F5: แชร์ในองค์กรและเสริมความทน (ไม่บังคับ)
- admin อัปโหลด learned profile ให้ทั้งองค์กรผ่านหลังบ้าน
- แจ้งเตือนเมื่อระบบเปลี่ยนหน้าจน signature ไม่ตรง, รายงานอัตราจับคู่สำเร็จ (ไม่มีข้อมูลเอกสาร)

## 6. การทดสอบ

- **ชุดฟิกซ์เจอร์ HTML** หลายแบบ ใน `test/fixtures/forms/` และเพิ่มหน้าใน `demo-extension`: ลงรับ (เดิม), ลงส่ง, หนังสือเวียน, บันทึกข้อความ, ฟอร์มที่ label เป็นตาราง, ฟอร์มที่ label อยู่ใน `placeholder`, ฟอร์มที่ใช้ select2, ฟอร์มใน iframe, ฟอร์มที่โหลดทีหลัง (SPA) และฟอร์มที่เขียนศัพท์คนละคำ (เช่น "ชื่อเรื่อง" แทน "เรื่อง")
- Unit test: label resolution, matcher (คะแนน, ความกำกวม, assignment), signature, validate ผลจาก AI (ปฏิเสธ selector นอก snapshot, ข้อความ injection ใน label)
- ทดสอบกับเว็บจริง Saraban แบบอ่านอย่างเดียว (สแกน) และกรอกข้อมูลสมมติแล้วคืนค่า ห้ามบันทึก เหมือนที่ทำไว้
- ตัวชี้วัด: อัตราจับคู่ถูก, **อัตรากรอกผิด (ต้อง 0)**, อัตราที่ต้องให้คนยืนยัน

## 7. ความเสี่ยง

| ความเสี่ยง | แนวทาง |
|---|---|
| label ไม่ชัด/อยู่ห่างช่อง | ใช้หลายแหล่ง + ตำแหน่ง, ไม่ชัดให้ผู้ใช้ยืนยัน |
| widget ที่ไม่ใช่ input มาตรฐาน (select2, datepicker, org-picker) | เก็บชนิด widget ใน snapshot, ตัวกรองแบบเฉพาะ widget ต่อยอดจากตัวกรอง select2 ที่มี ช่องที่กรอกไม่ได้ให้ระบุว่า "กรอกเอง" |
| select option ไม่ตรงค่าที่ได้จากเอกสาร | แมปด้วยข้อความ/ใกล้เคียง ถ้าไม่ตรงไม่เลือกและแจ้ง |
| หน้าเปลี่ยนหลังเรียนรู้ | signature + เตือนให้ตรวจ |
| prompt injection ผ่านข้อความหน้าเว็บ | validate ผลลัพธ์, ห้ามให้ AI สั่งการ, ส่งเฉพาะโครงสร้าง |
| กรอกผิดช่องในระบบจริง | ไม่กรอกอัตโนมัติถ้าไม่ชัวร์, ไฮไลต์ให้ตรวจ, ไม่กดบันทึก |

## 8. ประมาณงาน (หยาบ)

F1 ≈ 2–3 วัน, F2 ≈ 3–4 วัน, F3 ≈ 3–4 วัน, F4 ≈ 2–3 วัน, F5 ≈ 2–3 วัน (รวมทดสอบ/เอกสารแล้ว ไม่รวมรอข้อมูลจากลูกค้า)

## 9. สิ่งที่ต้องยืนยัน

1. ลำดับความสำคัญ: เริ่มจาก F1–F3 (ไม่ใช้ AI) ก่อน แล้วค่อย F4 ใช่ไหม (แนะนำ เพราะโควตา AI ยังไม่มี และกฎ+พจนานุกรมครอบคลุมส่วนใหญ่)
2. หน้าที่ต้องรองรับก่อน (ลงรับ, ลงส่ง, หนังสือเวียน, บันทึกข้อความ?) และมีหน้าอื่นที่ลูกค้าใช้จริงอีกไหม ขอตัวอย่างหน้าหรือสิทธิ์เข้าดูเพื่อทำฟิกซ์เจอร์
3. Learned profile: เก็บในเครื่องผู้ใช้อย่างเดียว หรือให้ admin แชร์ทั้งองค์กรด้วย (F5)
4. ระดับการกรอก: ช่องความมั่นใจ "กลาง" ให้กรอกเองพร้อมเตือน หรือรอผู้ใช้กดทุกครั้ง
5. v1 ของ leader คือ "อัปโหลดอย่างเดียว" ฟีเจอร์นี้เข้า v1 หรือเป็น v1.1

- เทสต์อัตโนมัติ `test/discovery.test.mjs` 15 ข้อ (jsdom ใน `eval/`) รวมทั้งชุด 54 ข้อผ่าน
- เว็บจริง saraban.rid.go.th (อ่านอย่างเดียว กรอกข้อมูลสมมติแล้วคืนค่าเดิม ไม่บันทึก):
  - หน้า "ลงรับ/สร้างเอกสาร": สแกนได้ 26 ช่องที่มองเห็น ป้ายชื่อถูกทุกช่อง (select2 5 ตัวอ่านตัวเลือกได้) จับคู่ถูก 10/10 ฟิลด์ระดับ "มั่นใจ" โดยไม่ใช้ selector ของ profile `saraban-rid` ช่องเลขทะเบียน/วันที่รับ/เวลารับไม่ถูกจับผิด
  - กรอกค่าสมมติด้วย selector จากการสแกน 10 ช่อง (รวม select2 ชั้นความเร็ว/ความลับ) ได้ครบ แล้วคืนค่าเดิมครบ
  - หน้า "สร้าง/หนังสือส่งภายใน": ใช้ id ชุดเดียวกับหน้าลงรับ แต่มีช่อง `prefixwid` (contenteditable ป้าย "เลขที่เอกสาร" ซ้ำกับ `txtwid`) และ "ประเภทเอกสาร" มีตัวเลือกเดียว ลายเซ็นฟอร์มจึงต่างจากหน้าลงรับ ตัวจับคู่ไม่เอา contenteditable เป็นคู่ของ doc_no จึงเลือก `txtwid` — **ยังต้องตรวจว่าหน้านี้ `txtwid` เป็นเลขลำดับหรือเลขเต็ม** ก่อนเปิดให้กรอกอัตโนมัติ
- ยังไม่ได้ทดสอบ: ปุ่มชี้ช่องและแผง side panel บน Chrome จริง (ต้องโหลด extension ใหม่แล้วลองเอง), หน้าอื่นของระบบ

## 11. ตรวจจับอัตโนมัติเมื่อสลับเมนู / แยกหน้าที่ไม่ใช่ฟอร์มกรอก (2026-10-21)

ระบบสารบรรณสลับเมนูโดย URL เดิม (`index.html`) และหลายหน้าใช้ id ชุดเดียวกัน จึงเพิ่ม:

- **เฝ้าหน้าอัตโนมัติ:** content script ใช้ MutationObserver + hashchange/popstate (เช็คไม่เกินวินาทีละครั้ง) เทียบ `quickSig` (หัวเรื่อง + รายการช่องที่เห็น) เปลี่ยนเมื่อไรแจ้ง side panel ให้ตรวจหน้า/สแกนใหม่เอง ไม่ต้องกดอะไร
- **แยกชนิดหน้า (`classifyPage`):** `form` (ฟอร์มกรอกหนังสือ) / `search` (ค้นหา รายงาน) / `unknown` ใช้หัวเรื่องหน้า (h1/h2), ช่องช่วง "เริ่ม…/ถึง…" ≥ 3 ช่อง และจำนวนช่องหลักที่จับคู่ได้ (ต้องมี "เรื่อง" + อีก ≥ 2) หน้าที่ไม่ใช่ `form` จะไม่ถูกใช้กรอกอัตโนมัติ
- **ค้นพบจากเว็บจริง:** หน้า "ค้นหาหนังสือ" ใช้ id `txtwid`, `txtfrom`, `txtto`, `txtwsubject` เหมือนหน้าลงรับ ทำให้ detect เดิมของ profile `saraban-rid` ตรงกับหน้าค้นหาด้วย (จะกรอกลงช่องค้นหา) แก้ด้วย `detectAll` (ต้องมี `#txtwdate` และ `#selwtype`) และ `detectNot` (ห้ามมี `#txtfdate`)
- ผลบนหน้าค้นหาจริง: จัดเป็น `search` ทั้งกรณีมีและไม่มีหัวเรื่อง
